# 양자화 — 방법과 수치 비교

LaS-Comp/TRELLIS 를 **8GB GPU 한 장(RTX 4070 Laptop, 8,188 MiB)** 에서 돌리기 위해 한 일과,
각 수단이 실제로 얼마를 줄였는지의 실측값.

구현: `tools/quantize_trellis.py` (저자 코드는 한 줄도 고치지 않고 **런타임 훅**으로만 붙인다)
측정: `tools/measure_vram.py` → `docs/vram_reports/*.json`

---

## 1. 출발점 — 왜 필요했나

| 실행 | 상태 | torch 예약 피크 | 여유 |
| --- | --- | --- | --- |
| 기준선 (양자화·오프로드 없음) | **error** `KeyError: 'sparse_structure_encoder'` | 5,590 MiB | — |
| fp8 만 | **OOM** | 7,376 MiB | 489 MiB |

fp8 양자화만으로는 못 들어간다. **양자화는 네 수단 중 하나**이고, 단독으로는 부족했다.

---

## 2. 방법 — 무엇을 어떻게 양자화했나

### 2-1. 가중치만 양자화 (weight-only)

`torchao.quantization.quantize_` 로 **Linear 층의 가중치만** 낮은 정밀도로 바꾼다.
활성값은 fp16 그대로다 — 활성 양자화는 정확도 위험이 크고, 이 모델의 병목은 가중치 상주 메모리였다.

```python
cfg = Float8WeightOnlyConfig()        # 또는 Int8WeightOnlyConfig()
quantize_(mod, cfg, filter_fn=_linear_filter)
```

RTX 4070 Laptop 은 **sm_89** 라 FP8 이 하드웨어로 지원된다(torchao 요구선 ≥ 8.9).

### 2-2. 대상 — 어떤 Linear 를 건드리고 무엇을 뺐나

`_linear_filter` 가 결정한다.

| 규칙 | 이유 |
| --- | --- |
| `Linear` 가 아니면 제외 | — |
| 이름에 `down_proj·fc2·proj_out·to_out·out_proj` 포함 → 제외 | 잔차 경로로 바로 더해지는 출력 투영. 오차가 누적된다 |
| **`in_features ≥ 2 × out_features` → 제외** | FFN down-projection 을 **모양으로** 잡는다 |
| `in_features < 256` 또는 `out_features < 256` → 제외 | 작은 층은 이득이 없고 오차만 는다 |

> **이름 규칙만으로는 놓친다.** TRELLIS DiT 의 FFN 은 1024→4096→1024 이고 층 이름이 `mlp.2` 라
> 위 이름 규칙에 걸리지 않는다. 첫 FP8 실행은 그래서 FFN down-proj 를 양자화하고 어텐션
> `to_out` 만 뺐다 — 의도와 반대였다. 모양 기준을 추가해 고쳤다.
> DiT 하나에 (4096,1024) 층이 24개 = 약 100 MiB 의 절감을 **포기하는 대신 품질을 지킨다.**
> 비교 실험용으로 `LASCOMP_QUANT_AGGRESSIVE=1` 이면 이 규칙을 끈다.

결과: 두 DiT 에서 **196개 중 122개**, **203개 중 123개**가 대상으로 잡혔다 (약 62%).

### 2-3. 절감 바이트를 재는 함정

torchao 의 `AffineQuantizedTensor` 는 **겉 dtype 이 fp16 처럼 보인다.**
`numel × element_size` 로 재면 양자화 전과 **같은 값**이 나와서, 처음에 절감이 `0.0 MiB` 로 찍혔다.

```python
impl = getattr(t, "tensor_impl", None)      # 서브클래스면 안쪽 저장 텐서를 직접 더한다
for a in ("int_data", "float8_data", "scale", "zero_point"):
    ...
```

### 2-4. torchao 버전 호환

이름이 버전마다 다르다 — 0.5.x 는 함수형(`float8_weight_only`), 최신은 Config 클래스형
(`Float8WeightOnlyConfig`). 둘 다 받게 하고, 없으면 설치 버전을 찍으며 죽는다.
환경은 **torchao 0.11 로 고정**했다.

## 3. 양자화 말고 쓴 세 가지 (이게 더 컸다)

### 3-1. 디코딩 전 오프로드 — `LASCOMP_OFFLOAD=1`

샘플링이 끝나면 더 쓰지 않는 모듈을 CPU 로 내린다:
`sparse_structure_decoder` · `sparse_structure_flow_model` · `slat_flow_model` ·
`sparse_structure_encoder` · `image_cond_model`(또는 `text_cond_model`).

| 실행 | 내림 전 | 내린 후 | **확보** |
| --- | --- | --- | --- |
| 이미지 조건 (fp8, IAS 0) | 4,473 MiB | 1,607 MiB | **2,866 MiB** |
| 이미지 조건 (fp8, IAS 1) | 3,201 MiB | 195 MiB | **3,006 MiB** |
| 텍스트 조건 (양자화 없음) | 4,986 MiB | 185 MiB | **4,801 MiB** |

### 3-2. 메시 추출을 CPU 로 — `LASCOMP_MESH_CPU=1`

FlexiCubes 표면 추출(res 256)을 CPU 에서 돌린다.

| | 값 |
| --- | --- |
| 추출 전 CUDA 점유 | 1,413 MiB |
| 추출 후 | 0 MiB |
| **확보** | **1,413 MiB** |

### 3-3. 디코딩 절약 재구성 — `LASCOMP_DECODE_LEAN=1` ★ OOM 을 실제로 푼 것

**증상**: 이미지 조건 + IAS 1 로 굽다리바리를 돌리면 **7,350 MiB 에서 OOM.**
위 두 수단을 다 켜도 났다.

**원인**: 디코더 업샘플 2단계의 `SparseGroupNorm32`. 입력이 3.05M × 96 채널인데,
fp32 사본을 여러 개 만들어 **입력의 약 8배**를 잡았다.

**고친 방법** — 두 모듈의 `forward` 를 갈아끼운다:

1. `SparseGroupNorm32.forward` — 통계는 fp64 로 누적하고, scale/shift 를 채널로 접어 넣은 뒤
   **4 MiB(2²²) 단위 조각으로 제자리(in-place) 연산**한다. 3.05M×96 이면 약 70 조각.
   ```python
   for i in range(0, n, rows_per):
       c = rows[i:i + rows_per].float()
       c.mul_(a).add_(sh)                 # 임시 텐서를 만들지 않는다
       orow[i:i + rows_per] = c.to(out.dtype)
   ```
2. `SparseSubdivideBlock3d.forward` — 중간 텐서 수명을 정리한다 (`del x` 로 조기 해제).

> **첫 시도는 ×0.86 밖에 못 줄였다.** 조각 크기를 2²⁵ 로 잡아서 전체가 한 조각이 됐고,
> `(rows.float() * a + sh)` 가 fp32 임시 텐서 3개를 만들었기 때문이다.
> 2²² + `mul_/add_` 로 바꿔 **×0.37** 이 됐다.

| | 디코딩 피크 |
| --- | --- |
| 훅 없음 | 7,350 MiB → **OOM** |
| 훅 있음 | **3,276 MiB** |

## 4. 수치 비교

### 4-1. 양자화 방식별 (같은 대상 bimba · 오프로드·메시CPU 켬 · IAS 0)

| 양자화 | 상태 | 프로세스 피크 | torch 예약 | 절감 바이트 | 여유 | 소요 |
| --- | --- | --- | --- | --- | --- | --- |
| **off** | ok | 5,061 MiB | 4,406 MiB | — | 3,127 MiB | 308.8 s |
| **int8** | ok | 4,609 MiB | 4,252 MiB | 770.0 MiB | 3,579 MiB | 316.8 s |
| **fp8** | ok | **4,573 MiB** | **4,232 MiB** | **776.0 MiB** | **3,615 MiB** | 292.2 s |

- fp8 과 int8 은 절감량이 거의 같다 (776 vs 770 MiB). fp8 이 피크·속도에서 조금 낫다.
- 양자화 없이도(off) 8GB 에 들어간다 — **오프로드·메시CPU 가 본질이었다.**
- 양자화의 기여는 **off 대비 약 488 MiB (프로세스 피크)**.

| `slat_flow_model` (fp8) | 203 | 123 | 1,147.9 MiB | 759.0 MiB | **389.0 MiB** |

### 4-5. 텍스트 조건 (text-xlarge · XL DiT)

| 양자화 | 상태 | 프로세스 피크 | 소요 |
| --- | --- | --- | --- |
| fp8 | **전부 NaN** | — | — |
| **off** | ok | 6,295 MiB | 598.1 s |

> **미해결**: FP8 로 text-xlarge 의 XL DiT 를 돌리면 출력이 전부 NaN 이다.
> 구간을 좁혀 확인한 것 — CLIP 정상 · fp16 DiT 정상 · **FP8 DiT 만 NaN.**
> 양자화 없이 돌려서 우회했다(6,295 MiB 로 8GB 에 들어간다). `tools/diag_fp8_nan_layer.py` 를 남겨 뒀다.
> image-large 에서는 같은 문제가 없다 — XL 폭(1536)에서만 나타난다.

## 5. 채택 설정

```bash
LASCOMP_QUANT=fp8  LASCOMP_OFFLOAD=1  LASCOMP_MESH_CPU=1  LASCOMP_DECODE_LEAN=1
```

`tools/run-lean.sh` 의 `fp8 1 1` + 디코딩 절약 훅. 실측 피크 **4,529 ~ 4,910 MiB** (8,188 중),
여유 3,200 MiB 이상.

## 6. 품질에 미친 영향

- 양자화로 형태가 눈에 띄게 달라지지는 않았다 (fp8 / int8 / off 의 bimba 결과를 비교).
- 다만 **FFN down-projection 과 출력 투영을 뺀 상태**에서의 관찰이다. `LASCOMP_QUANT_AGGRESSIVE=1`
  로 다 양자화하면 약 100 MiB 를 더 얻지만 품질은 확인하지 않았다.
- 디코딩 절약 훅은 **수치적으로 같은 결과**를 낸다 — 조각 정규화는 fp64 누적 + 제자리 연산이라
  재구성일 뿐 근사가 아니다 (`tools/test_decode_lean.py` 로 확인).

## 7. 정리

| 수단 | 확보 | 성격 |
| --- | --- | --- |
| 디코딩 전 오프로드 | 2,866 ~ 4,801 MiB | 가장 큼 |
| **디코딩 절약 재구성** | **약 2,059 MiB** (디코딩 피크 7,350 → 3,276) | OOM 을 실제로 푼 것 |
| 메시 추출 CPU | 1,413 MiB | 확실 |
| **fp8 가중치 양자화** | **776 MiB** (off 대비 피크 −488 MiB) | 보조 |

**양자화는 네 수단 중 가장 작다.** 이름에 속으면 안 되는 부분이다 —
8GB 에 들어가게 만든 것은 오프로드와 디코딩 재구성이고, 양자화는 여유를 더한 정도다.
